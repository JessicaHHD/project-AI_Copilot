# 新人价自动化工具 Vision

文档版本：2026-08-09  
适用范围：新人价自动化项目的产品愿景、作品集叙事和后续版本规划。  
当前定位：AI 产品经理作品集 Demo 优先，本地半自动工作流优先，不追求生产级平台化。

## 1. 一句话愿景

把新人价运营从“反复下载、拆表、查价、提报、回填”的手工流程中解放出来，让每个批次都能以可追踪、可暂停、可复盘的方式安全闭环。

## 2. 背景与机会

新人价提报不是单一表格处理，而是一条跨系统、跨角色、跨文件的批次工作流：运营需要从大盘订单源表中筛选候选商品，拆分查价 SKU，进入后台查价，等待 Outlook 邮件结果，再整合查价结果并计算新人价；随后还要给业务确认、生成提报文件、进入后台报名、导出审核结果、回填提报状态，并把结果作为下一批复提依据。

当前脚本已经覆盖多数重复性动作，但用户感知仍停留在“多个菜单和多个文件夹”。产品化机会在于：把脚本能力包装成面向运营的批次看板，让用户先理解“当前批次走到哪一步、下一步做什么、关键文件在哪里、风险在哪里”，再逐步接入更高自动化能力。

## 3. 核心用户

### 3.1 一线新人价运营

- 目标：快速完成一批商品的查价、确认、提报与审核回填。
- 痛点：文件多、后台入口多、邮件结果多、重复提报风险高。
- 关注：当前批次是否完整、哪些文件可用、下一步该做什么、是否会误上传历史文件。

### 3.2 运营负责人 / 业务协同方

- 目标：了解新人价提报效率、失败原因和批次沉淀状态。
- 痛点：过程不可视，异常依赖口头同步，复盘成本高。
- 关注：提报成功率、失败原因、业务确认结果、可复提机会。

### 3.3 AI 产品经理作品集评审者

- 目标：判断候选人是否能把真实业务脚本包装成可理解、可演示、可迭代的产品。
- 痛点：单纯代码脚本很难体现产品判断、边界意识和风险控制。
- 关注：用户旅程、MVP 范围、Demo 叙事、PRD 完整度、风险分层。

## 4. 北极星指标

批次提报闭环效率和安全性。

### 4.1 效率指标

- 单批次人工操作时长下降。
- 人工复制、整理、改名文件次数下降。
- 查找关键结果文件的时间下降。
- 异常定位时间下降。

### 4.2 安全指标

- 历史文件误上传次数下降。
- 查价结果误整合次数下降。
- 真实提报前的人工确认完整率提升。
- 每批次关键产物可追溯率提升。

### 4.3 体验指标

- 用户能在 1 分钟内说明当前批次状态。
- 用户能在页面中找到下一步建议和关键目录。
- 新用户能按阶段理解流程，而不是记菜单编号。

## 5. 产品原则

1. **先可视，再自动化**：先让批次状态、阶段、文件和日志可见，再考虑把高风险动作搬到 GUI。
2. **人机协同优先**：业务确认、真实提报、审核导出等关键风险动作保留人工确认。
3. **批次是核心对象**：所有输出、状态、日志、复提依据都围绕批次沉淀。
4. **低风险入口先行**：刷新、打开目录、打开日志、启动现有命令行优先；真实执行按钮后置。
5. **不改核心规则**：产品包装不改变筛品、查价、Outlook 下载、后台提报等既有逻辑。

## 6. 目标体验

用户打开“新人价自动化批次看板”后，应能立刻回答 5 个问题：

1. 当前处理的是哪一批？
2. 当前处于准备、查价、确认、提报、审核回填中的哪一步？
3. 下一步建议是什么？
4. 关键结果文件在哪里？
5. 如果出错，应该先看哪个日志或目录？

## 7. 产品分层

### 7.1 Vision 层

回答“为什么要做”：把脚本项目提升为可理解的运营批次工作台，突出效率、安全、可追溯。

### 7.2 MVP Case Study 层

回答“如何作为作品集讲清楚”：用 1 分钟 Demo 展示真实痛点、MVP 取舍、页面能力和下一步规划。

### 7.3 Full PRD 层

回答“如果继续产品化怎么做”：沉淀角色、流程、功能需求、验收标准、风险控制、路线图。

## 8. 版本路线

| 版本 | 目标 | 核心能力 | 不做 |
| --- | --- | --- | --- |
| V0 CLI 工作流 | 跑通本地批次闭环 | 筛品、拆分、查价、下载、整合、提报、审核回填 | GUI 体验 |
| V1.0 GUI MVP | 可录制 Demo 的批次看板 | 批次概览、5 阶段看板、关键文件、日志入口、低风险按钮 | 真实提报按钮、复杂配置编辑 |
| V1.1 工作台增强 | 提升可解释性 | 品池概览、异常摘要、React 前端壳、只读 API | 重写核心脚本 |
| V1.2 服务化接口 | 降低前端与脚本耦合 | 统一服务层、任务状态、可观测日志、接口契约 | 多用户权限 |
| V2 平台化 | 支撑团队协作 | 多批次管理、权限、审核流、报表和通知 | 单机脚本依赖 |

## 9. 成功画面

作品集 Demo 中，评审者看到的不只是“我写了脚本”，而是：

- 真实业务流程被拆成可理解的产品阶段。
- 高风险动作被刻意保留为人工确认。
- 批次清单、文件命名、日志目录形成可追溯闭环。
- GUI 先解决“看见流程和结果”的问题，而不是盲目替代命令行。
- 后续 PRD 能自然延展到服务化和平台化。

## 10. 关键风险与边界

- **业务规则风险**：筛品、新人价计算、复提判断必须沿用现有脚本，不在 GUI MVP 中改规则。
- **后台操作风险**：真实提报、审核导出仍通过命令行和二次确认完成，避免页面误触。
- **数据误用风险**：历史 PART、历史查价导出和疑似误下载文件需要隔离和提示。
- **Demo 过度承诺风险**：作品集表达中必须明确当前版本是本地半自动工具，不是多人在线 SaaS。
- **依赖风险**：Streamlit、FastAPI、React/Vite 依赖需本机具备环境；演示前需单独检查。
