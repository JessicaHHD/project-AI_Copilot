# 新人价自动化工具 MVP Case Study

文档版本：2026-08-09  
案例定位：AI 产品经理作品集 Demo。  
展示目标：用 1 分钟讲清楚“真实业务痛点 → MVP 取舍 → 可运行看板 → 后续路线”。

## 1. Case Study 摘要

新人价运营每个批次都要在源表、后台、Outlook、Excel 和审核结果之间来回切换。项目最初是多个 Python 脚本，已经能处理筛品、查价、提报和回填，但对非技术用户来说，最大问题不是“脚本有没有能力”，而是“不知道当前批次到哪一步、下一步做什么、结果文件在哪里”。

因此，本 MVP 没有急着把所有脚本按钮化，而是先做“新人价自动化批次看板”：读取现有配置、批次清单、输出目录和日志，展示批次状态、5 个流程阶段、关键文件和低风险操作入口，让用户能看懂一个批次的进度与产物。

## 2. 我的角色

- 业务流程梳理：把原始脚本能力映射为运营可理解的批次旅程。
- MVP 定义：把首版范围收敛为看板展示和低风险入口，不替代完整命令行流程。
- 信息架构：围绕“批次概览、流程阶段、关键文件、日志入口”组织页面。
- 风险控制：将真实提报、审核导出、业务确认保留在人工确认链路。
- 文档包装：沉淀 Vision、Case Study、Full PRD，支撑作品集讲述。

## 3. 用户问题

### 3.1 原始流程

一批新人价提报通常包含：

1. 获取大盘订单源表。
2. 按规则筛选候选 SKU。
3. 拆分查价前 SKU PART 文件。
4. 上传后台查价并导出到邮箱。
5. 从 Outlook 下载查价结果。
6. 整合查价结果并计算新人价。
7. 发送业务确认并接收确认表。
8. 生成提报 PART 文件。
9. 后台报名提报。
10. 导出审核结果并整理回填。
11. 沉淀下一轮复提依据。

### 3.2 关键痛点

| 痛点 | 用户表现 | 产品机会 |
| --- | --- | --- |
| 流程长 | 记菜单、找文件、等邮件 | 用阶段看板解释当前进度 |
| 文件多 | 输出目录、日志目录、PART 文件混在一起 | 用关键文件卡片聚合入口 |
| 风险高 | 历史文件可能误上传，真实提报不可误触 | 保留命令行二次确认，页面只做低风险入口 |
| 复盘难 | 出错后不知道看哪个日志 | 展示最近日志和异常入口 |
| 价值难展示 | 脚本能力对非技术评审不直观 | 包装成 1 分钟可演示工作台 |

## 4. MVP 范围

### 4.1 本次做什么

- 单页批次看板。
- 批次概览：批次名、环境、批次日期、输出目录、日志目录、批次清单状态、下一步建议。
- 流程阶段：准备任务、筛品查价、业务确认、后台提报、审核回填。
- 关键文件：新人价整合表、查价失败 SKU、ERP 文本、提报文件目录、提报情况整理表、批次清单、日志目录、疑似误下载目录。
- 低风险按钮：刷新、打开输出目录、打开日志目录、启动现有命令行工具。
- 产品说明：当前版本以批次看板为核心，完整流程执行仍通过现有命令行工具完成。

### 4.2 本次不做什么

- 不改筛品规则、查价逻辑、Outlook 下载逻辑、后台提报逻辑。
- 不把真实提报做成页面按钮。
- 不做审核导出按钮、自动发邮件、配置编辑器。
- 不做实时进度条、多用户权限、多页面复杂 GUI。
- 不替代 `run.bat`、`run_test.bat` 原有使用方式。

## 5. 解决方案

### 5.1 信息架构

页面按运营决策顺序组织：

1. **先看批次**：确认是不是正确批次和正确环境。
2. **再看阶段**：判断当前卡在哪一步。
3. **再看文件**：打开结果、目录或日志。
4. **最后操作**：只提供刷新和打开入口，必要时启动命令行工具继续执行。

### 5.2 当前 Demo 入口

| 入口 | 作用 | 风险级别 |
| --- | --- | --- |
| `run_gui.bat` | 打开 Streamlit 单页批次看板 | 低 |
| `run_workbench.bat` | 启动只读 API + React 工作台 | 低 |
| `run_gui_api.bat` | 单独启动只读 API | 低 |
| `run_frontend.bat` | 单独启动 React 前端 | 低 |
| `run.bat` | 启动正式命令行工具 | 中，需要按菜单和确认执行 |
| `run_test.bat` | 启动隔离测试命令行工具 | 低，写入测试目录 |

### 5.3 页面亮点

- 把“菜单编号”转成“业务阶段”。
- 把“散落文件夹”转成“关键文件结果”。
- 把“脚本运行结果”转成“下一步建议”。
- 把“危险按钮”后置到命令行确认链路。
- 把“脚本项目”包装成“批次运营工作台”。

## 6. 1 分钟 Demo 脚本

### 0-10 秒：问题引入

“新人价运营不是单纯处理一张表，而是一个跨 Excel、后台和 Outlook 的批次流程。过去用户需要记住多个脚本菜单、手动找文件、判断下一步。”

### 10-25 秒：展示批次概览

“我把核心对象抽象成批次。打开看板后，用户先看到批次名、环境、批次日期、输出目录、日志目录和下一步建议。”

### 25-40 秒：展示流程阶段

“中间是 5 个固定阶段：准备任务、筛品查价、业务确认、后台提报、审核回填。它不是为了炫技做进度条，而是帮助运营判断当前该做什么。”

### 40-50 秒：展示关键文件

“右侧或下方聚合关键产物：新人价整合表、查价结果、提报文件、提报情况整理表、批次清单和日志目录。用户不用再翻文件夹。”

### 50-60 秒：强调 MVP 取舍

“首版只做低风险入口，完整流程仍通过原命令行工具执行。这样既能演示产品价值，又不破坏已经跑通的业务脚本，后续再逐步服务化。”

## 7. Demo 成功标准

- 用户能通过 `run_gui.bat` 或 `run_workbench.bat` 打开页面。
- 页面能展示批次信息、5 个流程阶段和关键文件入口。
- 页面文案面向运营，不要求用户理解 Python 模块名。
- 页面明确说明完整流程仍通过现有命令行完成。
- 不触发真实提报、审核导出、自动发邮件等高风险动作。

## 8. 已沉淀能力

| 能力 | 当前状态 | 对用户的价值 |
| --- | --- | --- |
| 批次命名 | 已有 | 输出围绕批次组织，便于查找和复盘 |
| 工作流向导 | 已有基础版 | 串联阶段并在人工节点暂停 |
| 测试隔离 | 已有 | 用 `test_workspace` 验证，不影响正式文件 |
| 历史文件归档 | 已有 | 降低误上传、误整合风险 |
| 真实提报保护 | 已有 | `dry_run`、`upload_only`、`submit` 分层，并要求二次确认 |
| 批次看板 | 已有 MVP | 让非技术用户理解状态、文件和下一步 |
| React 工作台壳 | 已有 MVP | 支撑更像产品界面的 Demo 展示 |

## 9. 设计取舍

### 9.1 为什么先做看板，不先做全按钮化

新人价流程中真正高风险的动作是后台真实提报和审核导出。首版如果把所有动作都做成页面按钮，容易产生误触风险，也会把大量时间消耗在重写已稳定的脚本入口上。看板方案能以较小成本解决“看不懂、找不到、说不清”的问题，更适合作品集 Demo。

### 9.2 为什么保留命令行

命令行工具已经具备完整流程和安全确认机制。MVP 阶段让 GUI 读取状态、解释流程、打开目录即可，不破坏已有使用方式，也方便现场演示失败时退回稳定入口。

### 9.3 为什么强调批次

批次是新人价运营的自然工作单位。围绕批次组织文件、日志、提报状态和复提依据，能把一次性脚本变成可持续维护的运营系统。

## 10. 结果与下一步

### 10.1 当前结果

- 从脚本项目升级为可演示的批次工作台。
- 从技术菜单升级为运营阶段语言。
- 从散落文件升级为关键产物导航。
- 从“能跑”升级为“能讲清楚产品价值”。

### 10.2 下一步规划

1. 在只读 API 基础上定义任务服务接口。
2. 将低风险步骤逐步接入 GUI，例如配置检查、文件扫描、结果打开。
3. 为中风险步骤增加任务状态、日志流和撤销/确认机制。
4. 保持真实提报等高风险动作的二次确认和审计记录。
5. 增加批次复盘报表，用于展示成功率、失败原因和复提机会。
